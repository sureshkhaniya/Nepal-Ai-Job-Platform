# Security Baseline

## Authentication

- Normalize Nepal phone numbers to E.164 (`+977...`).
- OTP codes are short-lived, single-use, attempt-limited, and never stored in plaintext.
- Rate-limit by phone, IP, and appropriate account/device signals.
- Use anti-enumeration responses where practical.
- OAuth state/nonce and redirect URI validation are mandatory.
- Sessions use secure, HTTP-only cookies where browser architecture permits.

## Authorization

Backend checks must evaluate both role and resource relationship.

Examples:
- Candidate may modify only their own profile/resumes/applications.
- Employer may manage a company/job only with an active company membership granting that action.
- Employer may read applications only for jobs belonging to authorized companies.
- Admin capabilities are explicitly scoped and audited.

Never use `role = EMPLOYER` alone as permission to access every company.

## Resume/file security

- Private object storage.
- Strict size limits.
- MIME/signature validation.
- Sanitized filenames; storage keys are generated by the server.
- No execution of uploaded content.
- Extraction runs in a constrained worker context.
- Signed URLs are short-lived when used.
- Do not expose object storage credentials to clients.

## AI privacy and safety

- Minimize candidate PII sent to providers.
- Do not log full resume plaintext/prompts by default.
- Validate AI output structurally.
- Treat resume/job text as untrusted content, not executable instructions.
- AI cannot autonomously make final hiring/rejection decisions.
- Store model/prompt versions for auditability.

## Payments

- Merchant secrets are server-side only.
- Server owns price calculation.
- Verify provider responses/status before entitlement.
- Idempotency protects duplicate callbacks.
- Audit payment state changes.
- Never log secrets/signing keys.

## API

- Schema validation on all boundaries.
- Parameterized database access through the selected data layer.
- Bounded pagination and upload sizes.
- CORS limited to required origins.
- Security headers on web responses.
- CSRF protection for cookie-authenticated state changes according to framework/session design.
- Rate limiting for auth, application spam, search abuse, and payment initiation.

## Secrets

Never commit:
- `.env`
- database credentials
- Redis credentials
- OAuth client secrets
- SMS API secrets
- eSewa merchant secrets
- AI API keys
- cloud/storage keys

Commit `.env.example` containing names and safe placeholders only.

## Logging

Structured logs may contain IDs and operational metadata, but must avoid passwords, OTPs, auth tokens, full resume text, unnecessary personal data, and payment signing secrets.

Use correlation IDs to connect API requests, application IDs, AI job IDs, and payment IDs.

## Audit logging

Audit important privileged actions such as:
- admin moderation
- company verification
- employer role/membership changes
- payment reconciliation/overrides
- subscription entitlement changes
- security-sensitive account actions

Audit records should include actor, action, target, timestamp, safe metadata, and request correlation identifier.

## Backups and recovery

- Automated PostgreSQL backups.
- Periodic restore testing.
- Object-storage durability/versioning strategy where feasible.
- Redis loss must not destroy authoritative business records.
- Document recovery objectives before launch.

## Pre-launch security checklist

- [ ] Authentication abuse tests
- [ ] Broken-object-level authorization tests
- [ ] Employer cross-company access tests
- [ ] Admin authorization tests
- [ ] File upload validation tests
- [ ] Payment replay/idempotency tests
- [ ] AI prompt/content isolation tests
- [ ] Secrets scan
- [ ] Dependency vulnerability scan
- [ ] HTTPS/security header verification
